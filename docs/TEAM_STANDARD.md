## 2. Coding rules

These are the few that actually prevent the project from breaking when four people's work comes together. Keep it to these.

1. **Config is the single source of truth.** Feature names, vessel names, colours and thresholds live in `config/*.yaml`, never hardcoded in Python or TypeScript.
2. **Same names everywhere.** Targets are `CAD`, `LAD`, `LCX`, `RCA` (uppercase). The 3D mesh nodes are named exactly `LAD`, `LCX`, `RCA`. Features use `snake_case`, defined once in `features.yaml`. API, frontend and CV all use these.
3. **Leakage guard.** Never use `LAD`, `LCX`, `RCA` or `Cath` as input features, and no vessel label as a feature for another vessel. One small test checks this.
4. **Freeze the API contract early (by 3 Oct).** `api/schemas.py` is the contract: one `/predict` returns probabilities + SHAP + physiology + counterfactuals together; `/meta` returns features, ranges, bands and mesh map. The frontend reads `/meta` instead of copying values.
5. **Mock mode.** `/predict` returns a fixed valid payload when `API_MOCK=1`, so the frontend is never blocked waiting on the model.
6. **Probabilities are floats 0 to 1.** Rounding and percent signs happen only in the UI.
7. **Holdout touched once.** Save split IDs in `data/processed/holdout_ids.json`; only `evaluate.py` reads it, for the final numbers.
8. **Numbers come from `reports/`.** Every metric in the docs, README or video is generated by a script, not typed by hand.
9. **One environment.** Python 3.11, deps in `requirements.txt`. Node 20 for `web/`. If you add a package, add it to the list and tell the team.
10. **Runnable from a clean clone.** `pip install -r requirements.txt`, then documented commands to train, serve and run the web app. If it only works on your laptop, it is not done.

Light conventions: `print` is fine while developing, use `logging` in anything that ships. Seed everything with `42`. Keep the disclaimer (decision support and educational only, not a substitute for diagnostic imaging) always visible in the UI. Risk is never shown by colour alone (add a label or icon). Keep total meshes under ~150k triangles so it runs without a GPU.

## 3. Git: push straight to main

Small team, short timeline, so everyone pushes to `main`. No pull requests, no branch protection. To keep it from breaking:

- **`git pull` before you start and before you push.** Resolve conflicts immediately.
- **Stay in your own folder.** The structure splits work so people rarely touch the same files (ML in `pipeline/`, backend in `api/`, 3D in `web/src/viewer/`, etc.). The one shared file is `config/`, so say something in the group chat before editing it.
- **Commit small and often** with a clear message (`add calibration to train.py`, not `stuff`).
- **Never commit** data dumps, `.env`, secrets, `node_modules`, or notebook outputs (that is what `.gitignore` is for).
- **Keep `main` working.** If you push something broken, fix it or revert right away so you do not block the others.

One real risk with pushing to main: if two people edit the same file and someone force-pushes, work gets lost. So nobody uses `git push --force` on `main`, ever.

## 4. Division of labour

| Person | Owns |
|---|---|
| Person-1 | ML and validation — `pipeline/`, `models/`, `reports/`, `config/features.yaml` |
| Person-2 | Backend + dashboard — `api/`, `common/`, deploy, `config/manifest.yaml`, `web/src/dashboard/`, `web/src/api/` |
| Person-3 | 3D and anatomy — `web/src/viewer/`, `web/public/models3d/`, `config/risk_bands.yaml` |
| Person-4 | CV + docs — `cv/`, `slm/`, `docs/`, demo video |

**Person-1 — ML and validation**
Data cleaning and `features.yaml`; the leakage audit; models (logistic regression baseline, random forest, gradient boosting, calibrated ensemble); cross-validation + a locked holdout + confidence intervals; the five required metrics (accuracy, precision, recall, F1, ROC-AUC) plus Brier and calibration; SHAP per target; external validation on the UCI set; counterfactuals.
Delivers: v1 models by 6 Oct; calibration + external validation by 8 Oct.

**Person-2 — Backend, integration and dashboard**
Repo scaffold on day 1; the FastAPI `/predict` and `/meta` endpoints + mock mode, contract frozen 3 Oct; the dashboard (input form, probability cards, SHAP waterfall, physiology panel showing each value vs its reference range, what-if sliders, patient and clinician views); deployment (frontend on Vercel, API on Railway or Render) with the live URL in the README.
Delivers: mock `/predict` + types on 3 Oct; real model wired in on 6 Oct; deployed on 12 Oct.

**Person-3 — 3D and anatomy**
Day-1 asset audit: are LAD, LCX, RCA separable meshes and how many triangles? Decide real meshes vs spline-tube fallback. Then the viewer: vessels recolour from probability, rotate/zoom/click to isolate, heartbeat and risk glow, uncertain vessels shown desaturated or hatched, SHAP drivers pinned to anatomy, the 17-segment bullseye overlay. Keep it smooth on a no-GPU laptop.
Delivers: asset audit on 3 Oct; vessels coloured from the mock API by 5 Oct.

**Person-4 — CV, SLM and documentation**
Report reader: image or PDF -> clean up -> OCR -> extract fields (synonyms, units, range checks) -> confirmation screen before predicting. Measure field accuracy on synthetic reports. SLM is a stretch goal, only if the core is solid (decide 8 Oct) — natural language to tool calls, with a rule-based fallback that always works. Assembles the 6-page doc, README, architecture diagram, the 3–10 min YouTube demo and the Devpost entry.
Delivers: report reader by 11 Oct; docs and video on 13 Oct.

**Shared:** everyone reviews the leakage audit and the final README, and writes the docs section for their own part.

### What we are scored on (verified against the official Track A problem statement)

| Criterion | Weight | Owner |
|---|---|---|
| Predictive performance | 30% | Person-1 |
| 3D visualization | 25% | Person-3 |
| Clinical interpretability | 20% | Person-1 (SHAP) + Person-2 (dashboard) |
| System integration | 15% | Person-2 |
| Technical implementation | 10% | everyone (clean, reproducible repo) |

The five criteria add up to 100%. There is no separate line for "innovation", "multimodal", "generative" or "agentic", even though those are the hackathon's overall themes. So anything outside these five earns no direct points.

### Extras priority (built only after the core is done, 8 Oct)

Ranked by whether they actually score:

1. **Counterfactuals** — do count (feed Clinical Interpretability 20% and the dashboard side of System Integration). Build first.
2. **Report reader (CV)** — ~0 direct rubric points; demo and "multimodal" flavour only. Build if time allows.
3. **SLM** — ~0 direct rubric points; pure demo flair, plus a hosting headache on a no-GPU budget. Build last, cut first.
